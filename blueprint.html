General notes

  1. Every product is a deployed system, not a SaaS: your databases, keys, queues, delivery accounts and operations.
  2. Extension points are C# interfaces, not a DSL. Extensions run in your host and debug with the rest of your app.
  3. Every seam ships a safe default, so a fresh host runs before any of them is implemented.
  4. Everything that can be a setting is a setting. Code is for the seams.
  5. Each product ships an Angular admin SPA that your API host serves in-process; there is no separate frontend deployment.
  6. Each store has its own EF Core migrations history; a production host brings its own migrations assembly.

02.1 Identity and access management base unituser packagesIndice.Features.Identity.{Core, Server, SignInLogs, UI, AdminUI}, Indice.Features.ActivityLogs

ASP.NET Core Identity stores the users and Duende IdentityServer speaks OIDC / OAuth2. Indice adds the grants, MFA, devices, audit and UI. Workforce, partners and customers sign in through one pipeline.

Official partnerIndice is an official distributor and integrator of Duende Software. duendesoftware.com (opens in a new tab)
  1. One sign-in pipelinePassword or external provider (Apple, Google, Microsoft, Facebook, GovGr), then MFA, then the post-login validation activities, then tokens.
  2. Custom grantsFive grant types on top of the standard flows: totp, mfa, device_authentication, delegation and urn:indice:guest. The same IExtensionGrantValidator seam is open to you.
  3. Six MFA methodsSMS, Email, Viber, Authenticator app (TOTP), Trusted device (push approval over the /mfa SignalR hub) and FIDO2 / WebAuthn.
  4. Devices and sessionsA new device becomes trusted only after TrustActivationDelay (48 hours in the template). Server-side sessions are rows you can revoke; EnforceSingleActiveSession ends older sessions.
  5. Hardening and audit20 per-endpoint rate-limit rules, reCAPTCHA v3 with v2 fallback, lockout, password history. Two audit trails: sign-in logs with impossible-travel checks, and activity logs.

02.2 Case management and business workflows base unitcase type packagesIndice.Features.Cases.{Core, Server, Workflows, UI}

A case type is a JSON Schema form, a set of checkpoints and an Elsa workflow that decides who acts next. Customers and back-office staff work on the same record through two APIs.

  1. Process as dataA new process is a case type (schema, layout, checkpoints) plus a workflow, not a code change. Workflows are edited and published from the designer at /workflow without a redeploy.
  2. Two views, one recordmy/* serves customers, manage/* serves staff. Private checkpoints stay internal; the customer sees the last public checkpoint and the published data version.
  3. Actions come from the workflowGET manage/cases/{id}/actions asks the workflow which blocking activities are waiting (assign, edit, approve, custom actions). The SPA renders exactly those.
  4. Three-layer access controlRoles (CasesUser, CasesManager, CasesAdministrator), record-level access rules, and ownership. Four-eyes approval is a workflow activity: Block previous approver.
  5. Everything is a rowCheckpoints, data versions, comments and approvals live in CasesDb; the timeline is a query. A PDF per case type renders from a Razor template.

02.3 Multichannel campaigns and notifications base unitcampaign packagesIndice.Features.Messages.{Core, AspNetCore, Worker, Worker.Azure, UI}

A campaign fans out to Inbox, Push, Email and SMS according to its settings and each recipient’s preferences. Transactional messages (OTPs, receipts, alerts) run through the same pipeline.

  1. One campaign, four channelsMessageChannelKind is a [Flags] enum: Inbox 1, PushNotification 2, Email 4, SMS 8. Content is authored per channel and rendered per recipient with Handlebars (Full, Partial and Layout templates).
  2. Preference-aware deliveryChannels are resolved per recipient when the campaign is sent: campaign channels, narrowed by the recipient’s preference for the message type, minus what they cannot receive. IgnoreUserPreferences covers true system messages.
  3. API enqueues, worker deliversThe API accepts and queues; the worker resolves, renders and sends. Systems send through the send API under the narrower messages:send scope and get 202 Accepted.
  4. Vendors are configurationEmail: SMTP, SendGrid, SparkPost, Brevo, Azure Communication Services. SMS / Viber: Yuboto, Yuboto Omni, Apifon, Twilio, Vonage, SmsUp, KapaTEL, Mstat. Push: Azure Notification Hubs to APNS and FCM v1.
  5. Analytics off the hot pathEvents are queued and batched into MessageEvent records. KPIs: Reached, Engaged, Acted, Coverage. Click tracking rewrites links to /_tracking/… and redirects.

02.4 Risk assessment for transactions and activity base unitrisk rule packagesIndice.Features.Risk.{Core, Server, UI}, Indice.Features.GeoIP

A risk rule is a C# class that looks at an operation. Its thresholds are settings operators change at runtime. POST api/risk returns one score and one level (None, Low, Medium, High) with a reason per rule.

  1. Policy as code plus dataDetection logic is reviewed, versioned and unit-tested like the rest of your software. Thresholds, lists and switches live in RiskDb and hot-reload (every 5 seconds in the template) without a redeploy.
  2. Configurable scoringLevel ranges are configuration (template: 0, 1–1000, 1001–2000, 2001–3000). Aggregation is Sum, where risk accumulates, or Maximum, where the worst rule decides. Overlapping ranges stop the host at startup.
  3. Verdicts you can explainEvery assessment is stored with its input and per-rule score, level and reason, whether or not the operation goes ahead. A recorded event carries the ResultId of its verdict.
  4. History for rulesPOST api/risk/events records what happened. IRiskEventStore.GetList(subject, names, dates, filters) gives rules velocity, frequency and first-time-beneficiary checks.
  5. Offline geolocationMaxMind GeoLite2 databases ship with the product. The IP address resolves to country and coordinates inside the host; nothing leaves it.
