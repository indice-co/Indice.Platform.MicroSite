INDICE Platform · .NET and Angular

Self-hosted .NET solutions for identity, case workflows, messaging and risk.

For engineering teams in financial services, fintech and the public sector that keep data, signing keys and operations in their own environment. Each solution runs inside your ASP.NET Core host, on your SQL Server, with REST APIs and an embedded Angular admin UI that your developers extend in C#.

§ 01Platform foundation

One open-source foundation under every solution.

Cases, IAM, Messaging and Risk are assembled from the same Indice.Platform libraries, published on NuGet and npm. Your team works with standard ASP.NET Core, EF Core and Angular tooling, not a proprietary runtime.

  1. 01

    Open-source libraries

    Indice.Platform packages on NuGet and @indice/ng-* packages on npm provide the APIs, data access, authentication and UI components every solution uses.

    NuGet · npm
  2. 02

    Your host, your data

    Each solution is a set of libraries you compose in your own ASP.NET Core host, with its own SQL Server database and EF Core migrations. Nothing runs as SaaS.

    ASP.NET Core · EF Core
  3. 03

    One identity model

    Every solution is an OAuth2 API resource with its own scopes, such as cases, messages:send and risk. Operators sign in to each admin UI through your identity server.

    OIDC · OAuth2
  4. 04

    Extension points in C#

    Contact providers, lookups, risk rules, sign-in steps, log enrichers and workflow activities are C# interfaces with no-op defaults. Extensions run and debug in your process.

    Interfaces · DI
  5. 05

    Embedded admin UIs

    Each solution serves its Angular back office from its own API host: the Cases back office, the IAM admin at /admin, and the Messaging and Risk consoles. No separate front-end deployment.

    Angular
  6. 06

    Regulated requirements as features

    Four-eyes approval, two audit trails, impossible-travel checks, terms re-acceptance and data retention ship as configuration, informed by INDICE’s fintech experience.

    Fintech experience

§ 02Under the hood

How each solution works

The problem each solution addresses, how it works, how it is deployed and what it connects to.

02.1

Cases

Case management and back-office workflows

Key APIs
  • POST my/cases
  • GET manage/cases/{id}/actions
  • GET manage/dashboard/metrics
Stack
  • ASP.NET Core
  • EF Core · SQL Server
  • Elsa Workflows 2
  • JSON Schema + JSON Forms
  • Angular
Read the Cases technical reference

Cases runs form-driven processes, such as applications, service requests and approvals, on one record shared by customers and back-office staff. Customers submit from your apps, staff open cases on their behalf, and both follow the same assignment, edit and approval workflow.

The problem

Request-and-approval processes tend to live in inboxes, spreadsheets or one-off screens. Each new process becomes a development project, and it is hard to show who approved what or what the customer was told.

How it works
  1. Define a case type: a JSON Schema for the data, a JSON Forms layout and the checkpoints the case moves through.
  2. Publish an Elsa 2 workflow tagged with the case type from the designer at /workflow, without a redeploy.
  3. On submit, the workflow decides who acts next. The back office shows only the actions waiting: assign, edit, approve, reject or a custom action.
  4. Private checkpoints and data versions keep internal steps internal; the customer sees the public status and published data.
Architecture

One ASP.NET Core host runs the Cases API, the Elsa workflow server and designer, and the embedded Angular back office. CasesDb holds cases and WorkflowDb holds workflow state, so a workflow upgrade never touches case data.

Integrations
  • Customer search through IContactProvider, with an Identity Server provider built in
  • Form prefill from your systems with ICaseDataInitializer
  • Dropdown values from your systems through named ILookupService sources
  • Platform events such as CaseSubmittedEvent and a workflow-integration API
  • SMS, Viber and SMTP notifications from workflow activities
  • A PDF per case type through ICasePdfService

02.2

IAM

Identity and access management

Key APIs
  • my/account/*
  • api/my/devices
  • grant_type=device_authentication
Stack
  • ASP.NET Core Identity
  • Duende IdentityServer
  • EF Core · SQL Server
  • SignalR
  • Angular

IAM is an OpenID Connect and OAuth2 server for workforce, customer and partner sign-in. It builds on ASP.NET Core Identity and Duende IdentityServer and adds sign-in pages, MFA, device trust, audit logs, self-service APIs and an admin UI.

The problem

Teams either rent identity as a service and give up control of user data and signing keys, or rebuild login, MFA, device management and audit for every application.

How it works
  1. Every sign-in, by password or external provider such as Apple, Google, Microsoft, Facebook or GovGr, runs through one pipeline.
  2. MFA by SMS, email, Viber, authenticator app, push approval on a trusted device, or FIDO2 / WebAuthn, optional or enforced.
  3. A post-login chain handles terms re-acceptance, MFA onboarding, email and phone confirmation and password expiry before tokens are issued.
  4. Sign-in logs record every attempt with device and location and detect impossible travel; activity logs record every change.
Architecture

One ASP.NET Core host serves the Razor login pages, OIDC endpoints, management and self-service APIs, the /mfa SignalR hub and the Angular admin UI. Identity, configuration, operational, sign-in log and activity log data live in five databases that can share a server or sit apart.

Integrations
  • Your web, mobile and API clients over OpenID Connect and OAuth2
  • External providers: Apple, Google, Microsoft, Facebook, GovGr and any standard OIDC provider
  • Delivery providers for SMS, Viber and email, and Azure Notification Hubs for push
  • Custom grants for device sign-in, delegation, TOTP step-up and guest access
  • Platform events for users, clients, devices and logins
  • API resources for Cases and Messaging seeded by the template

02.3

Messaging

Multichannel campaigns and notifications

Key APIs
  • messages:send
  • MyMessages inbox API
  • analytics/*
Stack
  • ASP.NET Core
  • EF Core · SQL Server
  • Azure Storage / Service Bus
  • Handlebars.Net
  • Angular

Messaging delivers marketing campaigns and transactional messages, such as OTPs, receipts and alerts, over in-app inbox, push, email and SMS or Viber from one pipeline, with templates, audiences, recipient preferences and analytics.

The problem

Campaigns and system notifications often run on separate tools and vendor accounts. Consent and channel preferences are checked inconsistently, and every template is tied to one vendor.

How it works
  1. A campaign carries per-channel content, target channels, an audience from a distribution list or CSV import, and a schedule. Nothing is sent until it is published.
  2. Your systems send transactional messages with one call under the messages:send scope, through the same pipeline.
  3. A worker resolves each recipient, renders Handlebars templates per channel and keeps only the channels the recipient chose and can receive.
  4. Delivery and engagement events roll up into Reached, Engaged, Acted and Coverage metrics.
Architecture

The API host enqueues and serves the embedded Angular admin UI; a worker on Azure Functions or an in-process host renders and delivers. Azure Storage Queues or Service Bus connect them, with MessagesDb on SQL Server and Blob storage for attachments.

Integrations
  • Email through SMTP, SendGrid, SparkPost, Brevo or Azure Communication Services
  • SMS and Viber through Yuboto, Apifon, Twilio, Vonage and other gateways
  • Push through Azure Notification Hubs to APNS and FCM
  • Contacts, consent and preferences resolved from your identity server
  • A transactional send API for other systems
  • Tracked call-to-action links for click analytics

02.4

Risk

Real-time risk scoring for transactions and activity

Key APIs
  • POST api/risk
  • POST api/risk/events
  • GET risk-events/session/{sessionId}
Stack
  • ASP.NET Core
  • EF Core · SQL Server
  • NetTopologySuite
  • MaxMind GeoLite2
  • Angular

Risk scores operations such as payments, transfers, logins and profile changes in real time, before your application commits them. Rules are C# classes; their thresholds are settings that operators change at runtime.

The problem

Fraud checks are often duplicated inside each application or hidden in an external service, so thresholds need a release and decisions cannot be explained afterwards.

How it works
  1. Before committing an operation, your application calls POST api/risk with the subject, type, amount, IP address and any JSON data.
  2. The engine resolves the IP address to a location with the bundled GeoLite2 databases and runs every enabled rule.
  3. Results combine into one score and level, from None to High, by Sum or Maximum. Your application allows the operation, asks for MFA or blocks it.
  4. Record the completed operation with POST api/risk/events and its ResultId; rules query that history for velocity and new-country checks.
Architecture

One ASP.NET Core host serves the risk API, the admin API and the embedded Angular console. RiskDb on SQL Server, with spatial support, stores events, results and rule options; options reload every few seconds.

Integrations
  • Calling applications through client-credentials clients with the risk scope
  • Step-up authentication with your identity server, for example MFA on a Medium score
  • Offline GeoIP enrichment with bundled MaxMind GeoLite2 data
  • Custom event, result and rule-option stores
  • FluentValidation for each rule’s options
  • An admin API for investigation tools

§ 04Questions

What technical teams ask first

Is this a SaaS solution?
No. Each solution is a set of .NET libraries and an Angular UI that run in your own ASP.NET Core host, against your own SQL Server databases, signing keys and delivery accounts.
What do we need to run it?
ASP.NET Core hosting, SQL Server and an OpenID Connect identity server, which IAM provides. Redis, Azure Storage, Service Bus and Notification Hubs are used where a solution needs caching, queues or push.
Can we start with one solution?
Yes. Each solution has its own libraries, database and admin UI. Every solution you add reuses the same hosting, identity server and extension patterns.
How do we customise behaviour without forking?
Through C# extension points registered in your host, such as risk rules, workflow activities, sign-in steps, contact providers, lookups and log enrichers, and by overriding IAM pages and back-office UI strings.
Where do audit trails and history live?
In your databases. Cases stores every checkpoint, data version and approval; IAM keeps sign-in and activity logs; Risk stores every assessment with each rule’s reason; Messaging records delivery and engagement events.
What does INDICE do after go-live?
Ongoing support: new features, regular security updates with CVE patching, immediate technical assistance, and development of new extensions as requirements change.
